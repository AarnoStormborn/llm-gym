A hands-on roadmap for LLM fine-tuning and post-training

A progressive curriculum for learning the whole loop—data, training objectives, task environments, rewards, and evaluation—with small/open models and accessible or reproducible data. This is an educational plan, not a leaderboard or production recipe.

Progressive exercisesSmall-model firstEvaluation-ledNo training code included
Working principle: write the shared loaders, task rules, reward functions, evaluation adapters, and runners by hand when you start implementing them. Use mature libraries for model loading/training primitives only where they help you inspect rather than hide the learning objective. No datasets or model weights have been downloaded as part of this research.

Recommendation at a glance

Start with a baselineBuild the test cases and metrics before training; preserve the original model’s results.
Use synthetic data firstGenerated invoices, tool fixtures, Wordle episodes, and exact-answer tasks are cheap and controllable.
Progress from SFT to RLSFT → LoRA comparison → preferences/DPO → explicit rewards → GRPO/RLVR.
Keep every claim narrowReport task scores, error cases, regressions, data/model provenance, compute, and limitations.

The strongest first exercise is text-to-structured extraction on a small generated invoice corpus. It offers exact ground truth, an easy-to-understand SFT objective, deterministic schema checks, and a private held-out set. CORD can later add OCR/layout complexity, but it is not a plain-text-only dataset. For tool calling, use a tiny local tool environment and test it independently before selecting a BFCL subset. For RL, start with a transparent verifier/reward and a short horizon; GRPO is an advanced exercise, not the first training loop.

This synthesis combines six independently assigned research topics—project ideas, datasets, environments/runners, evaluation, fine-tuning techniques, and benchmarking—and checks central data claims against official cards or papers. Recheck licenses and pinned revisions at the point of use.

Project sequence

Each exercise should produce a reproducible comparison, not just a checkpoint. The model/task/data should stay small enough that you can inspect individual examples and explain what changed.

Why this order?

First establish what the original model can do and how to measure it. SFT then teaches the basic training path; LoRA isolates parameter efficiency; DPO introduces preference data without an online rollout loop. Tool use adds execution and state. A game/reward task makes RL mechanics observable. GRPO comes last because generation groups, reward design, and rollout throughput add complexity and compute. The sequence is a teaching recommendation, not a universal ranking of methods. TRL documentation distinguishes the relevant SFT, DPO, and GRPO trainer interfaces [18–20].

Data-selection cautions and synthetic alternatives
  • FUNSD: it is a small scanned-form benchmark (199 forms), useful for a visual/OCR extension, but I did not establish a clear permissive license from the sources reviewed. Do not select it until rights are checked. [8]
  • Wordle: no external training corpus is required. Use a legally obtained or generated word list, deterministic rules, and seeded answer splits. Test duplicate-letter feedback and invalid actions before training.
  • RLVR: generate integer arithmetic/string tasks with an exact verifier. Hold out generator rules, ranges, and seeds; inspect reward/answer disagreement. Avoid relying on a public benchmark test split for reward tuning.
  • Data governance: store source, revision, license, split manifest, and transformation/generator version. Keep large datasets and model outputs outside Git. Public data does not automatically mean unrestricted redistribution or commercial use.

Fine-tuning and post-training concepts

SFT — supervised fine-tuning. Learn target-token likelihood from demonstrations. Inspect the tokenizer/chat template, which tokens are masked from loss, and generated outputs—not just loss curves. Start with a tiny task and compare against the frozen base model [9][18].
LoRA / QLoRA — parameter-efficient tuning. LoRA freezes pretrained weights and learns low-rank updates; it is a method for adapting parameters, not a separate task or dataset [10]. QLoRA adds a quantized frozen base and is primarily a memory-saving path; kernels and model/sequence choices still matter [11]. Compare full SFT and LoRA on identical data and prompts.
DPO — offline preference optimization. Use prompt/chosen/rejected examples to favor preferred responses relative to a reference policy; it avoids training a separate reward model in the original formulation [12]. Preference quality and split hygiene are decisive. It is a useful first preference method, not proof that preferences generalize.
Reward-based RL / PPO. Sample model behavior, score it with a reward, and update the policy. PPO is an algorithm; an RLHF pipeline can add a reward model and reference/KL control, bringing more parts to inspect [13][14]. Start with a deterministic, auditable reward on a toy task.
GRPO and RLVR. GRPO compares a group of sampled completions for a prompt using their relative rewards and avoids a separate value model in the described method [15]. RLVR means the reward comes from verifiable outcomes (e.g., exact answer or valid solved game); it is not itself a unique optimizer. GRPO rollouts can be compute-heavy, and identical rewards within a group offer little ranking signal.
Fair comparison checklist
  • Use the same base checkpoint, tokenizer, chat template, train/validation/test prompts, decoding configuration, and evaluation code.
  • Do not pretend data signals are identical: SFT uses demonstrations, DPO uses preferences, and RL uses sampled trajectories plus reward. Document examples/tokens/rollouts and search effort.
  • Keep an untouched final test set. Record seed, model/data revisions, config, hardware, wall time, generation count, and cost.
  • Compare base → SFT → LoRA replicate → DPO → reward-RL/GRPO only on tasks that can fairly support each signal. Include regressions and failure examples.

Environments, runners, and shared helpers

Keep the learning boundaries visible. A useful conceptual pipeline is source/provenance → validate/normalize → split → task/environment → model + trainer → evaluator → run record. Each exercise can reuse the boundary contracts, while you hand-write the small, exercise-specific logic.

Write by hand firstDataset validators and split manifests; deterministic extraction metrics; Wordle transitions/reward; local fake tools; task-specific evaluation and run summaries.
Use as inspectable primitivesPyTorch tensors/autograd; Transformers model/tokenizer and Trainer; PEFT adapters; TRL SFT/DPO/GRPO; Accelerate for device/distributed launch.
Use only when it fitsGymnasium for sequential state/action environments such as Wordle. Plain document extraction does not need an RL environment API [16].
Minimal runner boundaries
  1. Data: validate the raw record and target format before tokenization; retain source IDs and revisions.
  2. Task: extraction/instruction are prompt-target tasks; Wordle/tool tasks need deterministic state, action validation, reward, termination, and seeding.
  3. Training: separate baseline inference, training, checkpoint/adapters, and post-training evaluation. Make one training batch inspectable before scaling.
  4. Evaluation: one frozen test protocol shared across model variants; measure task success and invalid behavior separately.
  5. Run record: persist model/tokenizer/data/config versions, seed, hardware, wall time, and cost outside large model artifacts.

Trainer and dataset APIs move. Use the versions in uv.lock as the project’s reproducibility anchor and check version-matched docs rather than copying online examples blindly [17–21].

Testing and evaluation protocol

  1. Freeze a baseline first: model and tokenizer revision, prompt/template, decoding settings, task cases, evaluator version, and split.
  2. Test infrastructure separately: data/schema validation, one-batch forward/backward/update smoke test, save/reload, and unit tests for edge cases in tools, environment transitions, reward, termination, and timeouts.
  3. Isolate data: training, tuning, public benchmark, and private final holdout are distinct. Never tune reward weights or prompts on the final test set. Document contamination risk instead of claiming it has been eliminated [22].
  4. Report behavior: task success + format/validity + per-category errors + qualitative examples + base-to-tuned regressions. Training loss and reward are diagnostics, not the final capability claim.
  5. Repeat and account: seeds, runtime, tokens/episodes, hardware, and cost. For stochastic training, report multiple runs where feasible; small exploratory runs should be described as such [23][24].

Statistical and judge caveats

Use paired comparisons on the same prompts where possible; show per-seed/per-category results and uncertainty rather than overinterpreting small score changes. LLM-as-judge methods can have length/position or model-family biases; randomize response order and retain human or deterministic checks where feasible [25].

Practical guardrails and next decisions

  • Model selection: choose a small/open checkpoint whose license, tokenizer/chat template, architecture, and current training-library support are clear. Record the exact revision; do not assume all “small” models support identical LoRA or GRPO paths.
  • Compute: use local Apple Silicon for data, evaluator/environment tests, inference, and the smallest training smoke tests. GRPO’s repeated generations can dominate runtime; measure before renting a GPU. GPU prices depend on SKU, region, and time, so estimate from a chosen Runpod offering rather than hard-coding a generic cost.
  • Reproducibility: version data manifests, generator seeds, model/tokenizer revisions, config, split, evaluator, and environment rules. Keep checkpoints, caches, and generated corpora out of Git.
  • Licensing: CC-BY-NC data is non-commercial; gated data requires explicit acceptance; dataset cards may not settle rights for source documents. Do not publish raw data or model artifacts without reviewing terms.
  • Implementation scope: this brief selects learning targets and research inputs; it intentionally does not create training scripts, loaders, environments, or benchmarks. Those are yours to implement when you ask.
Suggested first build: baseline a small instruct model on a handwritten set of generated text invoices; evaluate schema validity and field-level exact match on held-out templates; then train a tiny SFT run and compare. Add CORD only after deciding whether OCR/layout is in scope and confirming that the desired data use is covered.
